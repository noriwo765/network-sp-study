## Part A：IPヘッダ

### A1 ★【2-1】
IPv4ヘッダ（オプションなし）の長さは何バイトか。また IHL フィールドの値が `5` のとき、何を意味するか。

<details><summary>解答・解説</summary>

- **20バイト**。IHL は **4バイト（32ビット）単位**でヘッダ長を表すので、5 × 4 = 20バイト。
- IHL は4ビットなので最大値15 → 最大 **60バイト**（オプション最大40バイト）。
- 似た落とし穴：「全長（Total Length）」はヘッダ＋データの長さで**バイト単位**、「フラグメントオフセット」は**8バイト単位**。単位がフィールドごとに違う。
</details>

### A2 ★【2-2】
TTL の役割を説明せよ。また traceroute が TTL をどう利用して経路を調べているか説明せよ。

<details><summary>解答・解説</summary>

- ルータは転送のたびに TTL を **1減算**し、**0になったらパケットを破棄**して送信元へ **ICMP Time Exceeded（タイプ11）** を返す。目的はルーティングループ時にパケットが永久に回り続けるのを防ぐこと。
- traceroute は TTL=1, 2, 3… と増やしながら送信し、各ホップのルータから返る Time Exceeded の**送信元IPアドレス**を集めて経路を表示する。
- 主な ICMP タイプ：0 Echo Reply／3 Destination Unreachable／5 Redirect／8 Echo Request／11 Time Exceeded
</details>

### A3 ★【2-3】
IPヘッダのプロトコル番号について、次の値が示すプロトコルを答えよ。
`1` / `6` / `17` / `50` / `89`

<details><summary>解答・解説</summary>

| 番号 | プロトコル |
|------|-----------|
| 1 | ICMP |
| 6 | TCP |
| 17 | UDP |
| 50 | ESP（IPsec） |
| 89 | OSPF |

ついでに覚える：47 = GRE、51 = AH、112 = VRRP。
**OSPF はTCP/UDPを使わずIPに直接乗る**、という点は午後でも問われる（FWでの許可設定など）。
</details>

### A4 ★★【2-4】
MTU 1500バイトのリンクに、IPヘッダ20バイト（オプションなし）＋データ3000バイト（全長3020バイト）のパケットが送出される。DFビットは0である。
分割後の各フラグメントについて、**データ長・フラグメントオフセット値・MFフラグ**を答えよ。

<details><summary>解答・解説</summary>

1フラグメントに載せられるデータ = 1500 − 20 = **1480バイト**（8の倍数なのでそのまま使える）

| # | データ長 | オフセット値 | MF |
|---|---------|------------|----|
| 1 | 1480 | 0 | 1 |
| 2 | 1480 | 185（= 1480 ÷ 8） | 1 |
| 3 | 40 | 370（= 2960 ÷ 8） | 0 |

- オフセットは **8バイト単位**。だから最後以外のフラグメントのデータ長は8の倍数でなければならない。
- 3つのフラグメントは同じ **識別子（Identification）** を持ち、受信側（**最終宛先ホスト**）で再組立てされる。途中のルータは再組立てしない。
- MF（More Fragments）=1 は「後続あり」。最後だけ0。
</details>

### A5 ★★【2-4】
DFビットが1のパケットが、それより小さい MTU のリンクに転送されようとした。ルータの動作を答えよ。
また、その仕組みを利用する Path MTU Discovery が、FW の設定によって機能しなくなるのはどんな場合か。

<details><summary>解答・解説</summary>

- ルータはパケットを**破棄**し、送信元へ **ICMP Destination Unreachable（タイプ3／コード4：Fragmentation Needed and DF set）** を返す。このメッセージには**ネクストホップの MTU 値**が含まれる。
- 送信元はその MTU に合わせてパケットサイズを小さくして再送する（＝PMTUD）。
- FW で **ICMP を一律遮断**していると、この通知が送信元に届かず、大きいパケットだけが延々と捨てられる（**PMTUDブラックホール**）。症状は「ping や小さい通信は通るのに、Webページの表示やファイル転送が途中で止まる」。
- 対策：ICMP タイプ3 コード4 を許可する／ルータで **TCP MSS を書き換える（MSSクランプ）**。
</details>

### A6 ★★【2-4】
Ethernet（MTU 1500）で IPv4・TCP ともにオプションなしの場合の MSS はいくつか。
また PPPoE 回線（MTU 1492）の場合はいくつか。

<details><summary>解答・解説</summary>

- MSS = MTU − IPヘッダ(20) − TCPヘッダ(20)
- Ethernet：1500 − 40 = **1460バイト**
- PPPoE：1492 − 40 = **1452バイト**（PPPoEヘッダ6＋PPPヘッダ2 = 8バイト分 MTU が小さい）
- MSS は TCP の **SYN / SYN+ACK のオプション**で互いに通知する。
</details>

### A7 ★★【2-5】
NAT を行わないルータがIPパケットを転送するとき、**IPヘッダ内で書き換わるフィールド**を全て答えよ（フラグメントは発生しないものとする）。
また、IPヘッダ以外で書き換わるものは何か。

<details><summary>解答・解説</summary>

- IPヘッダ：**TTL** と **ヘッダチェックサム**（TTL が変わるのでチェックサムを再計算）
- **送信元・宛先IPアドレスは変わらない**
- IPヘッダ以外：**Ethernetヘッダの送信元・宛先MACアドレス**（ホップごとに付け替え）、FCS
- 補足：NAPT を行うとIPアドレス・ポート番号、それに伴い TCP/UDP チェックサムも変わる。DSCP をリマーキングする機器なら ToS も変わる。
</details>

### A8 ★★【2-3】
旧 ToS フィールドは現在どのように使われているか。また VoIP の音声パケットに一般的に付与される DSCP 値（PHB名と10進値）を答えよ。

<details><summary>解答・解説</summary>

- 8ビットのうち上位6ビットが **DSCP（DiffServ Code Point）**、下位2ビットが **ECN（明示的輻輳通知）**。
- 音声は **EF（Expedited Forwarding）= 46**（2進 101110）。最優先で低遅延キューに入れる。
- その他：AF（AF11〜AF43）＝帯域保証クラス、CS（Class Selector）＝旧 IP Precedence 互換、0 = ベストエフォート。
</details>

### A9 ★★【2-6】
`192.168.10.100/26` について、ネットワークアドレス、ブロードキャストアドレス、割り当て可能なホスト数を答えよ。

<details><summary>解答・解説</summary>

- /26 → 第4オクテットのマスクは 255.255.255.**192**、ブロックサイズは 256 − 192 = **64**
- 区切り：0 / 64 / 128 / 192 → 100 は 64〜127 の範囲
- ネットワークアドレス：**192.168.10.64**
- ブロードキャストアドレス：**192.168.10.127**
- ホスト数：2^6 − 2 = **62**
</details>

### A10 ★★★【2-7】
IPv6 の基本ヘッダについて、IPv4 ヘッダと比べて**なくなった・変わった点**を3つ以上挙げ、それぞれの理由を述べよ。

<details><summary>解答・解説</summary>

| 変更点 | 理由・ポイント |
|-------|---------------|
| ヘッダ長が**固定40バイト**（IHLなし） | オプションは**拡張ヘッダ**として外出しし、ルータ処理を高速化 |
| **ヘッダチェックサムの廃止** | L2（FCS）や上位層で誤り検出しているため。TTL が変わるたびの再計算が不要 |
| **中継ルータでのフラグメント禁止** | 分割は**送信元のみ**（フラグメント拡張ヘッダ）。大きすぎれば ICMPv6 Packet Too Big を返す → PMTUD 必須。最小MTUは1280 |
| TTL → **Hop Limit** | 中身は同じ（ホップ数で減算） |
| Protocol → **Next Header** | 次の拡張ヘッダ or 上位プロトコルを示す |
| **フローラベル**の追加 | 同一フローの識別（QoS用） |

さらに：ARP は廃止され **NDP（ICMPv6）** に、ブロードキャストは廃止され**マルチキャスト**に置き換え。
</details>

## Part B：ルーティング

### B1 ★【4-1】
ルータに次の経路がある。各宛先へのパケットはどのネクストホップへ転送されるか。

| 宛先ネットワーク | ネクストホップ |
|----------------|--------------|
| 0.0.0.0/0 | R1 |
| 10.0.0.0/8 | R2 |
| 10.1.0.0/16 | R3 |
| 10.1.2.0/24 | R4 |

(1) 10.1.2.5　(2) 10.1.3.5　(3) 10.2.0.1　(4) 172.16.0.1

<details><summary>解答・解説</summary>

(1) **R4**　(2) **R3**　(3) **R2**　(4) **R1**

**ロンゲストマッチ**：宛先に一致する経路のうち、**プレフィックス長が最も長い（最も具体的な）経路**を選ぶ。
これは AD やメトリックより**先に**適用される。デフォルトルート（/0）は全てに一致するが最も短いので最後の手段になる。
</details>

### B2 ★★【4-1】【4-2】
同じ宛先 `192.168.50.0/24` について、スタティックルート・OSPF・RIP でそれぞれ経路を学習した。ルーティングテーブルに採用されるのはどれか。理由とともに答えよ。
また「フローティングスタティックルート」とは何か。

<details><summary>解答・解説</summary>

- **スタティックルート**が採用される。プレフィックス長が同じなので **AD（アドミニストレーティブディスタンス）** が小さいものが優先される。
- 代表的なAD（Cisco 既定値）：直接接続 0／スタティック 1／eBGP 20／OSPF 110／RIP 120／iBGP 200
- **AD はプロトコル間の優先度**、**メトリックは同一プロトコル内の優先度**。混同注意。
- **フローティングスタティック**：AD を動的ルーティングより**大きく**設定したスタティックルート。通常は OSPF 経路が使われ、OSPF 経路が消えたとき（主回線障害）だけ浮かび上がってバックアップ経路として使われる。
</details>

### B3 ★★【4-3】
次の4つの経路を1つに集約したときの集約経路を答えよ。
`10.1.8.0/24`、`10.1.9.0/24`、`10.1.10.0/24`、`10.1.11.0/24`

<details><summary>解答・解説</summary>

**10.1.8.0/22**

第3オクテットを2進数にする：
```
 8 = 0000 1000
 9 = 0000 1001
10 = 0000 1010
11 = 0000 1011
     ^^^^ ^^      ← 共通部分は上位6ビット
```
共通ビット = 8 + 8 + 6 = 22 ビット → /22、先頭は 10.1.8.0。

注意：集約経路が実在しないネットワーク（例：8〜11 のうち1つが別拠点にある）まで含むと、誤った方向へ転送したりループの原因になる。
</details>

### B4 ★★【4-5】
OSPF の基準帯域が既定値（100Mbps）のとき、10Mbps のリンクと 1Gbps のリンクのコストはそれぞれいくつか。
また、この既定値のままだと現代のネットワークで何が問題になるか。

<details><summary>解答・解説</summary>

- コスト = 基準帯域 ÷ インタフェース帯域
- 10Mbps：100 ÷ 10 = **10**
- 1Gbps：100 ÷ 1000 = 0.1 → 最小値1に切り上げ → **1**
- 問題点：100Mbps も 1Gbps も 10Gbps も全部コスト1になり、**帯域の違いを経路選択に反映できない**。
- 対策：全ルータで**基準帯域を揃えて引き上げる**（例：100Gbps）か、インタフェースごとに手動でコストを設定する。ルータ間で基準帯域がバラバラだと意図しない経路になる。
</details>

### B5 ★★【4-5】
OSPF のブロードキャスト型ネットワーク（Ethernet セグメント）で DR/BDR を選出する目的と、選出の基準を答えよ。
また、DR より優先度の高いルータを後から接続した場合、DR は交代するか。

<details><summary>解答・解説</summary>

- 目的：全ルータ同士で隣接関係（Full）を結ぶと n(n−1)/2 本になり LSA のやり取りが膨大になる。**DR/BDR とだけ Full** になり、DR が代表して LSA を配布することで負荷を減らす。
- 選出基準：① **OSPFプライオリティが最大** → ② 同値なら **ルータIDが最大**。プライオリティ **0** のルータは DR/BDR にならない。
- **交代しない**（プリエンプションなし）。現 DR が停止して初めて BDR が DR に昇格する。
- 補足：DROther 同士は **2-Way** 状態で止まる（Full にならない）。これは正常。
</details>

### B6 ★★★【4-5】
OSPF における ABR と ASBR とは何か。また、**スタブエリア**に設定すると、そのエリア内のルータにどんなメリットがあるか。

<details><summary>解答・解説</summary>

- **ABR（Area Border Router）**：複数のエリア（うち1つはエリア0）に接続し、エリア間の経路情報（Type3 LSA）を中継するルータ。
- **ASBR（AS Boundary Router）**：OSPF 外部の経路（スタティック・BGP など）を OSPF に**再配布**するルータ。外部経路は **Type5 LSA** として広告される。
- **スタブエリア**：ABR が **Type5（外部経路）を流さず、代わりにデフォルトルート**を注入する。エリア内ルータのLSDBとルーティングテーブルが小さくなり、CPU・メモリ負荷が下がる。
  - トータリースタブ：Type3 も遮断し、デフォルトルートのみにする。
  - NSSA：スタブだがエリア内に ASBR を置ける（Type7 LSA）。
- 原則：**全エリアはエリア0（バックボーン）に接続**しなければならない。
</details>

### B7 ★★★【4-6】
iBGP では、なぜ AS 内のルータを**フルメッシュ**でピア接続する必要があるのか。また、その負担を減らす方法を答えよ。

<details><summary>解答・解説</summary>

- eBGP は AS_PATH に自AS番号が含まれていれば破棄することでループを防ぐ。しかし iBGP では AS_PATH が変化しないのでこの方法が使えない。
- そこで **「iBGPピアから学習した経路を、他のiBGPピアに広告しない」**（iBGPスプリットホライズン）というルールがある。
- その結果、全ての iBGP ルータに経路を行き渡らせるには**フルメッシュ**が必要になる（n(n−1)/2 本のセッション）。
- 回避策：**ルートリフレクタ**（RR がクライアントから受けた経路を他クライアントに反射する）、または **コンフェデレーション**（AS 内をサブASに分割）。
- 補足：BGP は **TCP 179番**を使う。
</details>

### B8 ★★★【4-6】
自社 AS が2つの ISP（ISP-A、ISP-B）とマルチホーム接続している。次の要件を満たすために使う BGP 属性（または手法）を答えよ。

(1) 自社から**インターネットへ出ていく**通信は、ISP-A を優先したい
(2) インターネットから**自社へ入ってくる**通信は、ISP-A 経由を優先させたい

<details><summary>解答・解説</summary>

(1) **LOCAL_PREF**：ISP-A から受信した経路の LOCAL_PREF を高くする。**AS 内の全ルータ**（iBGPで伝わる）が ISP-A 側を出口に選ぶ。値が**大きいほど優先**。
(2) **AS_PATH プリペンド**：ISP-B に広告する経路の AS_PATH に自AS番号を複数回追加し、ISP-B 経由の経路を「遠く」見せる。（隣接ASが同じ相手なら **MED**（**小さいほど優先**）も使える）

覚え方：**出ていく（Outbound）＝ LOCAL_PREF、入ってくる（Inbound）＝ AS_PATH / MED**
主な選択順（抜粋）：Weight（Cisco独自）→ LOCAL_PREF 大 → 自ルータ発 → AS_PATH 短 → ORIGIN → MED 小 → eBGP > iBGP → IGPメトリック小
</details>

### B9 ★★★【4-7】
2台のルータ（RT1：優先度110 マスタ、RT2：優先度100 バックアップ）で VRRP を構成し、LAN 側に仮想IPを提供している。
RT1 の **WAN 側回線だけが切断**され、LAN 側は正常なままだった。このとき何が起こるか。また、その問題への対策を答えよ。

<details><summary>解答・解説</summary>

- VRRP は **LAN 側で VRRPアドバタイズメント**（マルチキャスト 224.0.0.18、プロトコル番号112）をやり取りしてマスタを監視している。LAN 側が正常なら RT1 はマスタのまま。
- → 端末は引き続き RT1 にパケットを送り、**WAN に出られず通信断**になる（もしくは RT1 が RT2 経由で迂回できる構成なら遠回り）。
- 対策：**インタフェーストラッキング**。RT1 の WAN 側 IF（または上流への到達性）を監視し、ダウン時に優先度を下げる（例：110 → 90）。RT2（100）のほうが高くなり、**プリエンプト**が有効なら RT2 がマスタになる。
- 補足：仮想MACアドレスは **00-00-5E-00-01-{VRID}**。切替時に端末の ARP テーブルを更新する必要がない。
</details>

### B10 ★【4-4】
RIP について、メトリックの指標と最大値、到達不能を表す値を答えよ。また、距離ベクトル型で発生する「カウントトゥインフィニティ」を防ぐ仕組みを1つ挙げよ。

<details><summary>解答・解説</summary>

- メトリックは**ホップ数**、最大 **15**、**16 = 到達不能**（だから大規模網には不向き）。
- 帯域を考慮しないので、遅い回線でもホップ数が少なければ選ばれてしまう。
- カウントトゥインフィニティ対策：
  - **スプリットホライズン**：経路を学習したインタフェースにはその経路を広告し返さない
  - **ポイズンリバース**：学習したインタフェースにメトリック16（到達不能）として広告し返す
  - **トリガードアップデート**：変化時に即座に通知する
</details>

## Part C：セキュリティ

### C1 ★【6-1】
A さんが B さんにメールを送る。次の目的で使う鍵は「誰の」「どちらの鍵（公開鍵／秘密鍵）」か答えよ。

(1) A がメールにデジタル署名を付ける
(2) B が署名を検証する
(3) A がメール本文を B だけが読めるように暗号化する（公開鍵暗号を使用）

<details><summary>解答・解説</summary>

(1) **A の秘密鍵**　(2) **A の公開鍵**　(3) **B の公開鍵**（復号は B の秘密鍵）

- 署名は「本人しか持たないもので作る」→ 送信者の秘密鍵。実際はメッセージの**ハッシュ値**を秘密鍵で署名する。これで**改ざん検知＋なりすまし防止（否認防止）**。
- 暗号化は「受信者だけが解けるように」→ 受信者の公開鍵。
- 実運用では公開鍵暗号は遅いので、**本文は共通鍵で暗号化し、共通鍵を公開鍵で送る**（ハイブリッド暗号）。
</details>

### C2 ★★【6-2】
Web ブラウザがサーバ証明書を受け取ったときに確認する項目を3つ以上挙げよ。
また、サーバに**中間CA証明書を設定し忘れる**と何が起きるか。

<details><summary>解答・解説</summary>

確認項目：
- **署名の検証**：発行元CAの公開鍵で証明書の署名を検証し、**ルートCA（ブラウザ/OSが信頼済み）までチェーンがつながる**か
- **有効期限**内か
- **失効していないか**（CRL または OCSP、OCSPステープリング）
- アクセスした **FQDN が証明書の SAN（CN）と一致**するか

中間CA証明書がないと、ブラウザはサーバ証明書からルートCAまでの**チェーンを構築できず、証明書エラー**になる（ブラウザによっては補完して表示できてしまうため、「一部の端末だけエラー」という形で表面化しやすい）。
</details>

### C3 ★★【6-3】
「前方秘匿性（PFS: Perfect Forward Secrecy）」とは何か。また TLS 1.3 で **RSA 鍵交換が廃止**された理由を、前方秘匿性と関連づけて説明せよ。

<details><summary>解答・解説</summary>

- **前方秘匿性**：サーバの秘密鍵が**将来漏えいしても、過去に記録された通信を復号できない**性質。
- RSA 鍵交換では、クライアントがセッション鍵の素（プリマスタシークレット）を**サーバの公開鍵で暗号化して送る**。通信を全部録っておけば、後でサーバ秘密鍵が漏れた時点で**過去の通信がすべて復号できてしまう**。
- **(EC)DHE** は通信ごとに使い捨ての鍵ペアで鍵を共有するので、サーバ秘密鍵（署名用にのみ使う）が漏れてもセッション鍵は復元できない。
- TLS 1.3 は鍵交換を **(EC)DHE のみ**にして PFS を必須化した。他に、**1-RTT ハンドシェイク**（0-RTT も可）、ServerHello 以降の暗号化、弱い暗号スイートの削除なども変更点。
</details>

### C4 ★★★【6-4】
IPsec の AH と ESP の違いを説明せよ。また、拠点ルータが NAPT 配下にある場合に IPsec VPN を張る際の問題と、その解決策を答えよ。

<details><summary>解答・解説</summary>

| | AH（プロトコル番号51） | ESP（プロトコル番号50） |
|---|---|---|
| 暗号化 | **なし** | **あり** |
| 認証・改ざん検知 | あり（**IPヘッダの不変部分も含む**） | あり（ESPヘッダ以降。外側IPヘッダは対象外） |
| NAT との相性 | **NG**（IPアドレス書換えで認証失敗） | ポート番号がないので NAPT 不可 → NAT-T で対応 |

NAPT 配下での問題：
- ESP には TCP/UDP のような**ポート番号がない**ため、NAPT が変換対象を識別できない。
- **解決：NATトラバーサル（NAT-T）**。IKE で NAT の存在を検出し、ESP パケットを **UDP 4500番**でカプセル化して送る。IKE 自体は **UDP 500番**（NAT検出後は4500へ移行）。
- 補足：拠点間 VPN は通常**トンネルモード**（元のIPヘッダごと暗号化し新IPヘッダを付与）、端末間は**トランスポートモード**。
</details>

### C5 ★★★【6-5】
ステートフルインスペクション型 FW を2台、別々の経路上に設置した（FW1 は行き経路、FW2 は戻り経路を通る非対称ルーティング）。内部から外部への TCP 通信が確立できない理由を説明せよ。

<details><summary>解答・解説</summary>

- ステートフルFW は、内部→外部の **SYN を通した時点でセッション情報（状態テーブル）を作り**、それに合致する戻りパケットだけを自動で許可する。
- 非対称経路だと、SYN は FW1 を通るので FW1 にだけセッションが作られる。戻りの **SYN+ACK は FW2 を通るが、FW2 には対応するセッションがない**ため、「いきなり来た不正なパケット」として**破棄**される → 3ウェイハンドシェイクが完了しない。
- 対策：行きと戻りが同じFWを通るよう経路を設計する（**対称化**）、FW 間で**セッション同期**する（冗長構成）、など。
- 静的パケットフィルタとの違い：パケットフィルタは戻りパケットも明示的に許可する必要があるが状態を持たない（その分、ポート番号を広く開ける必要がある）。
</details>

### C6 ★★【6-5】
IDS・IPS・WAF の違いを、設置形態と防御対象の観点で説明せよ。また、IPS で**誤検知（フォールスポジティブ）**が特に問題になる理由を述べよ。

<details><summary>解答・解説</summary>

| | 設置 | 動作 | 対象 |
|---|---|---|---|
| **IDS** | ミラーポート等で**通信を複製して監視** | **検知・通知のみ** | ネットワーク全般 |
| **IPS** | 通信経路上に**インライン**設置 | 検知して**遮断** | ネットワーク全般 |
| **WAF** | Webサーバの前（インライン or リバースプロキシ） | 検知・遮断 | **Webアプリへの攻撃**（SQLインジェクション、XSS など、HTTP の中身） |

- IPS はインラインで自動遮断するため、**誤検知すると正常な業務通信を止めてしまう**。IDS は通知だけなので業務影響はない。
- 逆に**フォールスネガティブ（見逃し）**は攻撃を通してしまう。導入初期は**検知モードで運用してチューニング**してから遮断モードにする、というのが定番の答え。
- インライン機器は**故障時に通信断**になる点もポイント（バイパス機能・冗長化）。
</details>

### C7 ★★【6-6】
IEEE 802.1X 認証の構成要素3つの名称と役割を答えよ。また EAP-TLS と PEAP の違いを、クライアント側の認証方法の観点で説明せよ。

<details><summary>解答・解説</summary>

| 要素 | 役割 | 例 |
|---|---|---|
| **サプリカント** | 認証を受ける端末側ソフト | PC、スマホ |
| **オーセンティケータ** | 認証を仲介し、結果に従いポートを開閉 | L2SW、無線AP |
| **認証サーバ** | 認証の可否を判定 | **RADIUS** サーバ |

- サプリカント↔オーセンティケータは **EAPOL**、オーセンティケータ↔認証サーバは **RADIUS** で EAP を運ぶ。
- **EAP-TLS**：サーバ・**クライアント双方が証明書**で認証。安全だがクライアント証明書の配布・管理が必要。
- **PEAP**：サーバ証明書で **TLS トンネル**を作り、その中でクライアントは **ID/パスワード**（MS-CHAPv2 など）で認証。クライアント証明書は不要。
- 認証結果に応じて **VLAN を動的に割り当てる**（ダイナミックVLAN）のも午後頻出。
</details>

### C8 ★★【6-7】
送信ドメイン認証の SPF・DKIM・DMARC について、それぞれ何を検証する仕組みか説明せよ。
また OP25B とはどのような対策で、正規ユーザはどうやってメールを送信するか。

<details><summary>解答・解説</summary>

- **SPF**：送信ドメインの DNS（TXTレコード）に**「このドメインのメールを送ってよいサーバのIPアドレス」**を登録し、受信側は**接続元IPアドレス**と照合する。転送されると失敗しやすい。
- **DKIM**：送信サーバがメールに**デジタル署名**を付与し、受信側は DNS に公開された**公開鍵**で検証する。改ざん検知もでき、転送にも強い。
- **DMARC**：SPF／DKIM の結果と**ヘッダFromのドメインが一致（アライメント）**するかを確認し、失敗時の扱い（none / quarantine / reject）を**送信ドメイン側がポリシーとして宣言**する。集計レポートを受け取れる。
- **OP25B（Outbound Port 25 Blocking）**：ISP が、自社の動的IPアドレスから**外部の 25番ポートへの通信を遮断**し、ボット化した端末からのスパム送信を防ぐ。
  - 正規ユーザは **サブミッションポート（587番）＋ SMTP-AUTH**（または 465番 SMTPS）で自分のメールサーバに送信する。
</details>

### C9 ★★★【6-7】
DNS キャッシュポイズニング攻撃の仕組みを説明せよ。また、その対策を2つ以上挙げよ。

<details><summary>解答・解説</summary>

- キャッシュDNSサーバ（フルリゾルバ）が権威DNSサーバに問い合わせている間に、攻撃者が**偽の応答を先に送り込み**、キャッシュに偽情報を記憶させる。以降、そのサーバを使う利用者が偽サイトへ誘導される。
- 偽応答が受理される条件は、**問い合わせIDと宛先ポート番号などが一致**すること。ID は16ビットしかないので総当たりされうる。
- **カミンスキー攻撃**：存在しないサブドメイン（random1.example.com …）を次々問い合わせさせ、キャッシュ済みでも攻撃を何度でも試せるようにした手法。
- 対策：
  - **送信元ポート番号のランダム化**（推測すべき組合せを増やす）
  - **DNSSEC**（権威サーバの応答に署名し、リゾルバが検証する）
  - キャッシュサーバを**オープンリゾルバにしない**（内部からの再帰問い合わせのみ許可）
  - 権威サーバとキャッシュサーバを**分離**する
</details>

### C10 ★★【6-8】
(1) SYN フラッド攻撃の仕組みと、サーバ側の代表的な対策を答えよ。
(2) DNS や NTP を悪用した**リフレクション（増幅）攻撃**で UDP が使われる理由を2つ答えよ。

<details><summary>解答・解説</summary>

(1)
- 攻撃者が送信元を偽装した **SYN を大量に送り**、サーバは SYN+ACK を返して **ACK を待つハーフオープン状態**のセッションを大量に抱える → 接続キュー（バックログ）があふれ、正規の接続を受け付けられなくなる。
- 対策：**SYN Cookie**（SYN 受信時に状態を保持せず、SYN+ACK のシーケンス番号に情報を埋め込んで ACK 受信時に検証）、FW/IPS のしきい値制御、ハーフオープンのタイムアウト短縮。

(2)
- **送信元IPアドレスを偽装しやすい**：UDP はハンドシェイクがないので、偽装した送信元（＝被害者）にそのまま応答が届く。
- **応答が要求より大きい（増幅率が高い）**：小さな問い合わせで大きな応答（DNS の ANY 応答、NTP の monlist 等）を被害者に送らせられる。
- 対策：オープンリゾルバ・不要な UDP サービスの停止、**送信元IP偽装の防止（イングレスフィルタリング）**。
</details>
