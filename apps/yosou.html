◎

QUIC／HTTP/3

TCP＋TLS の代わりに、UDP の上で暗号化と再送をまとめて行うプロトコル。

なぜ今　主要なブラウザ・CDN・動画サービスでは既に HTTP/3 が標準。社内では「FW や SWG で見えない UDP 通信が増えた」ことが課題になっている。

知っておくべきキーワード

UDP/443
QUIC の通り道。FW・プロキシで許可しないと TCP（HTTP/2）に戻る
TLS 1.3 を内蔵
暗号化の握手を接続と同時に済ませる → 1往復で通信を始められる
0-RTT
2回目以降は最初のパケットでデータを送れる（リプレイ攻撃に注意）
コネクション ID
IP アドレス・ポートが変わっても同じ接続とみなす → 回線の切替に強い
HoL ブロッキング
TCP は1つの損失で全ストリームが待つ。QUIC はストリームごとに再送
Alt-Svc
HTTP/2 の応答で「HTTP/3 も使える」と知らせるヘッダ
ヘッダまで暗号化
中継機器から中身が見えない → 可視化・制御がしにくい

ネスペならこう問われる

  1. HTTP/3 に対応したのに、社内の利用者だけ HTTP/2 で通信していた。FW の設定で考えられる原因は？
    解答例

    FW が UDP の 443 番ポートを許可しておらず、ブラウザが TCP に切り替えたため。

  2. スマートフォンが Wi-Fi から LTE に切り替わっても、QUIC の通信が切れない理由は？
    解答例

    IP アドレスとポート番号ではなく、コネクション ID で接続を識別しているから。

  3. HTTP/2（TCP）と比べて、パケットが1個失われたときの影響が小さい理由は？
    解答例

    TCP では1つの損失で全ストリームが待たされる（HoL ブロッキング）が、QUIC はストリームごとに再送を管理するので、他のストリームは止まらない。

◎

サーバ証明書の短期化と ACME

証明書の最長有効期間が段階的に短くなり、最終的に47日に。手作業の更新はもう回らない。

なぜ今　2025年に CA/ブラウザフォーラムで決定し、2026年3月から最長200日に短縮済み（ちょうど今年の話）。ACME による自動更新が前提になる。

知っておくべきキーワード

最長有効期間
398日 → 200日（2026/3〜）→ 100日（2027/3〜）→ 47日（2029/3〜）
ACME
証明書の申込み・ドメインの検証・発行・更新を自動化するプロトコル
HTTP-01
CA が 80 番で /.well-known/acme-challenge/ のファイルを取りに来る
DNS-01
_acme-challenge の TXT レコードで証明。ワイルドカード・社内サーバはこちら
TLS 終端
LB やプロキシで TLS をほどく構成。証明書はその機器に入れる
失効・OCSP
漏えいした証明書を無効にする仕組み。短期化は「失効に頼らない」方向

ネスペならこう問われる

  1. 有効期間の短縮に対して、運用面で必要な対策は？
    解答例

    ACME を使い、証明書の取得と更新を自動化する。

  2. ワイルドカード証明書を ACME で取得するときに使う検証方式は？
    解答例

    DNS-01（_acme-challenge の TXT レコードで、ドメインの管理者であることを示す）。HTTP-01 では取得できない。

  3. インターネットから 80 番に到達できない社内サーバでも DNS-01 なら取得できる理由は？
    解答例

    CA はサーバではなく DNS サーバ上の TXT レコードを確認するので、サーバ自体に外から到達できなくてもよいから。

  4. 負荷分散装置で TLS を終端している構成で、更新を忘れがちな機器は？
    解答例

    負荷分散装置（サーバではなく、TLS を終端している機器の証明書を更新する必要がある）。

◎

VPN 装置の脆弱性 → ZTNA（Zero Trust Network Access）

VPN は「入れたら社内LAN全体」。ZTNA は「人・端末を毎回確認して、許可したアプリだけ」。

なぜ今　警察庁の集計では、ランサムウェアの侵入経路の約8割が VPN 機器とリモートデスクトップ。2025年も国内の大手企業でランサムウェアによる業務停止が相次いだ。

知っておくべきキーワード

ゼロトラスト
社内・社外で区別せず、アクセスのたびに確かめる考え方
ZTNA
アプリ単位でつなぐリモートアクセス。VPN の置き換え
IdP・多要素認証
利用者の確認。パスワード＋スマホの承認など2つ以上の要素で
端末の状態確認
OS の更新・EDR の稼働・会社の管理端末か、を接続の条件にする
コネクタ
社内に置き、クラウドへ外向きに接続 → インターネットに公開するポートが要らない
最小権限・マイクロセグメンテーション
必要な相手とだけ通信させ、乗っ取られたときの広がりを抑える

ネスペならこう問われる

  1. VPN 装置が攻撃の入口になりやすい理由は？
    解答例

    インターネットに公開されていて誰でも接続を試せるため、脆弱性を悪用されると社内LANに入られてしまうから。

  2. ZTNA のコネクタが、社内からクラウドへ外向きに接続する方式の利点は？
    解答例

    FW でインターネットからの通信（インバウンド）を許可する必要がなく、攻撃の対象になる公開ポートがなくなる。

  3. VPN と比べて、乗っ取られたときの被害範囲を小さくできる理由は？
    解答例

    利用者ごとに許可したアプリケーションにだけ接続させ、社内LAN全体には到達させないから。

  4. 接続のたびに端末の何を確認する？
    解答例

    OS の更新プログラムの適用状況、EDR（ウイルス対策）が動いているか、会社が管理している端末か、など。条件を満たさない端末は接続させない。

関連：R4午後Ⅰ問2・R7午後Ⅰ問3（SWG）、R4午後Ⅰ問3（SSO）

◎

DDoS 攻撃への対策

大量の通信を自社の手前で受け止めて、正常な通信だけを通す。

なぜ今　2024年末〜2025年初めに、国内の航空会社や大手銀行のネットサービスが DDoS 攻撃でつながりにくくなった。IoT 機器を乗っ取ったボットネットが使われる。

知っておくべきキーワード

ボットネット
乗っ取られた IoT 機器などの集団。攻撃の発信元になる
スクラビング
通信を引き込んで攻撃だけを取り除く専門のセンター・サービス
CDN・WAF
手前で大量の通信を受け止め、オリジンサーバを隠す・守る
Anycast
同じアドレスを多拠点から広告し、攻撃を各拠点に分散させる
RTBH
攻撃対象の宛先への通信を上流で全部捨てる（そのサービスは止まる）
リフレクション（増幅）攻撃
送信元を標的に偽装し、DNS などの大きな応答を標的へ送らせる
SYN cookie
SYN Flood を受けても、接続待ちの表を使い切らないようにする工夫

ネスペならこう問われる

  1. CDN を導入したのに、Web サーバへの攻撃が止まらなかった。考えられる原因と対策は？
    解答例

    原因：オリジンサーバの IP アドレスが知られていて、CDN を経由せず直接攻撃された。対策：オリジンサーバは CDN からの通信だけを許可する。

  2. 攻撃を受けたときに、通信をスクラビング事業者に誘導する方法は？
    解答例

    BGP で自社のアドレスの経路を事業者から広告させ、攻撃対象宛ての通信を事業者経由にする。

  3. Anycast が DDoS に強い理由は？
    解答例

    同じ IP アドレスを複数の拠点から広告するので、攻撃の通信が各拠点に分散するから。

  4. RTBH（宛先のアドレスへの通信を上流で捨てる）の欠点は？
    解答例

    攻撃の通信だけでなく正常な通信も捨てるので、攻撃対象のサービスは止まってしまう（他のサービスは守れる）。

関連：R6午後Ⅰ問1（CDN）

耐量子計算機暗号（PQC）

量子コンピュータでも解けない暗号。TLS では従来の方式と組み合わせた「ハイブリッド」で使い始めている。

なぜ今　2024年に米国 NIST が ML-KEM などを標準化し、主要なブラウザは既に TLS の鍵交換で X25519MLKEM768（ハイブリッド）を使っている。米国などは2035年ごろまでの移行を目標にしている。

知っておくべきキーワード

ML-KEM
鍵交換に使う PQC（旧名 Kyber）。米国の標準 FIPS 203
ML-DSA
署名に使う PQC（旧名 Dilithium）。FIPS 204
ハイブリッド鍵交換
従来方式と PQC の両方で鍵を作り、合成して使う
X25519MLKEM768
主要なブラウザが TLS で使っているハイブリッド方式の名前
Harvest Now, Decrypt Later
今のうちに盗聴・保存し、量子計算機ができたら解読する
クリプトアジリティ
暗号方式を差し替えやすく作っておくこと

ネスペならこう問われる

  1. 量子コンピュータの実用化はまだ先なのに、今から対応する理由は？
    解答例

    今盗聴して保存した暗号文が、将来の量子コンピュータで解読されるおそれがあるから（Harvest Now, Decrypt Later）。

  2. PQC 単独ではなく、従来方式と組み合わせる（ハイブリッド）理由は？
    解答例

    新しい PQC に未知の弱点が見つかっても、従来方式が破られない限り安全を保てるから。

  3. PQC を有効にしたら、古いプロキシ経由の TLS 接続だけ失敗した。考えられる原因は？
    解答例

    ClientHello が大きくなって複数の TCP セグメントに分かれ、中継機器がそれを正しく処理できなかった。

○

DNS の HTTPS レコードと ECH

DNS で「HTTP/3 に対応しているか」と「ClientHello を暗号化する鍵」を配る。接続先のドメイン名（SNI）が見えなくなる。

なぜ今　HTTPS レコード（SVCB）は大手 CDN とブラウザが対応済み。ECH も主要ブラウザ・CDN で使われ始め、SNI でフィルタリングしている FW・SWG に影響が出ている。

知っておくべきキーワード

HTTPS レコード（SVCB）
対応プロトコル・IP アドレスのヒント・ECH の鍵を DNS で配るレコード
alpn=h3
HTTP/3 に対応しているという印
SNI
TLS の最初に平文で送る接続先のドメイン名。フィルタリングに使われてきた
ECH
ClientHello を暗号化。外から見えるのは CDN などの共通の名前だけ
DoH・DoT
DNS の問い合わせ自体を暗号化する（443番・853番）
TLS インスペクション
プロキシで TLS を復号して検査する。ECH への対策の一つ

ネスペならこう問われる

  1. HTTPS レコードを使うと、初回の接続から HTTP/3 を使える理由は？
    解答例

    DNS の応答（alpn）で HTTP/3 対応が分かるので、Alt-Svc ヘッダを受け取るのを待たずに QUIC で接続できるから。

  2. ECH が使われると、SWG の URL フィルタリングにどんな影響がある？
    解答例

    SNI で宛先を判断していると、本当の接続先のドメイン名が分からず、フィルタリングできなくなる。

  3. ECH の暗号化に使う公開鍵は、どうやってクライアントに配られる？
    解答例

    DNS の HTTPS レコード（ech パラメータ）で配られる。

Wi-Fi 7（IEEE 802.11be）

一番の新機能は MLO（マルチリンク）。複数の周波数帯を同時に使って、速く・途切れにくくする。

なぜ今　国内では2023年末に解禁され、対応する AP・スマートフォン・PC が普及期に入った。次の Wi-Fi 8（802.11bn）は速度より信頼性を重視している。

知っておくべきキーワード

802.11be
Wi-Fi 7 の規格名（Wi-Fi 6／6E は 802.11ax）
MLO
2.4／5／6GHz 帯の複数のリンクを同時に使う
320MHz 幅
6GHz 帯で使える最大のチャネル幅（Wi-Fi 6 は 160MHz）
4096QAM
1回に12ビット送る変調（Wi-Fi 6 の 1024QAM は10ビット）
プリアンブルパンクチャリング
チャネルの一部に干渉があっても、そこだけ避けて広い幅を使う
WPA3・PMF
6GHz 帯では必須。WPA2 だけの端末は 6GHz 帯につながらない
Wi-Fi 8（802.11bn）
次の世代。速度より信頼性・低遅延を重視

ネスペならこう問われる

  1. MLO によって可用性が上がる理由は？
    解答例

    複数の周波数帯の通信路を同時に使うので、一つが干渉で劣化しても他の通信路で通信を続けられるから。

  2. 6GHz 帯を使う利点と注意点は？
    解答例

    利点：新しく開放された帯域で干渉が少なく、広いチャネル幅を確保できる。注意点：電波が届く範囲が狭いので AP を増やす必要がある。

  3. WPA2 にしか対応していない端末が 6GHz 帯の SSID に接続できない理由は？
    解答例

    6GHz 帯では WPA3（または OWE）と PMF が必須だから。

関連：R5午後Ⅰ問3（高速無線LAN）

○

低軌道衛星をバックアップ回線に

地上の回線と経路が全く違うので、災害時の予備回線に向く。ただし CGNAT の内側になる。

なぜ今　低軌道衛星のインターネット（遅延は数十ms）を企業や自治体が BCP 用に導入。2025年には国内でスマートフォンと衛星の直接通信も始まった。

知っておくべきキーワード

低軌道（LEO）衛星
高度が低く、遅延は数十 ms。地上の回線と経路がまったく違う
CGNAT
事業者側でまとめて変換する NAT。外から着信できない
NAT トラバーサル
IPsec の ESP を UDP/4500 に包んで NAT を越える
フローティングスタティック
優先度を低くしておく予備の静的経路。主経路が消えたときだけ使う
IP SLA・トラッキング
宛先への到達性を監視し、届かなくなったら経路を切り替える
BCP
災害時も業務を続けるための計画。経路の違う予備回線を用意する

ネスペならこう問われる

  1. 衛星回線では、本社から拠点へ VPN の接続を開始できない理由は？
    解答例

    キャリアグレード NAT でプライベートアドレスが割り当てられ、外部からの接続を受けられないから。

  2. その環境で IPsec VPN を使うには？
    解答例

    拠点側から接続を開始し、NAT トラバーサル（ESP を UDP/4500 でカプセル化）を使う。

  3. 主回線の障害時に、自動で衛星回線に切り替えるには？
    解答例

    主回線の先への到達性を監視し、断を検知したら主回線の経路を消して、優先度の低い静的経路（衛星回線向け）を使わせる。

パスキー（FIDO2／WebAuthn）

パスワードの代わりに、端末の中の秘密鍵で署名してログインする。鍵はドメインごとに分かれている。

なぜ今　2025年にフィッシングによる証券口座の乗っ取りが多発し、証券会社などがパスキーや多要素認証を必須にした。

知っておくべきキーワード

FIDO2
WebAuthn（ブラウザ⇔サイト）と CTAP（端末⇔認証器）からなる規格
公開鍵暗号
サイトには公開鍵だけを置き、秘密鍵は端末から出さない
オリジンの検証
鍵がドメインに紐づく → 偽サイトのドメインでは使われない
チャレンジレスポンス
サイトが毎回違う乱数を送り、端末が秘密鍵で署名して返す
リプレイ攻撃
過去の認証データの使い回し。毎回違うチャレンジで防ぐ
AitM フィッシング
偽サイトが本物へ中継してワンタイムパスワードまで奪う。パスキーなら防げる

ネスペならこう問われる

  1. パスキーがフィッシングに強い理由は？
    解答例

    鍵がサイトのドメイン（オリジン）と結び付けて保存されていて、偽サイトのドメインでは署名しないから。

  2. サーバから認証情報が漏えいしても被害が出にくい理由は？
    解答例

    サーバには公開鍵しか保存されず、パスワードのような秘密の情報がないから。

  3. サーバが毎回違うチャレンジを送る理由は？
    解答例

    以前の署名を使い回すリプレイ攻撃を防ぐため。

関連：R4午後Ⅰ問3（SSO）

RPKI（BGP の経路の検証）

「このアドレスを広告してよいのはこの AS」という証明（ROA）で、偽の経路を捨てる。

なぜ今　BGP の経路ハイジャックや設定ミスによる経路漏れで、大規模な通信障害が繰り返し起きている。国内の ISP でも経路の検証（ROV）の導入が進んだ。

知っておくべきキーワード

RPKI
IP アドレス・AS 番号の持ち主を証明する仕組み
ROA
「このプレフィックスはこの AS が広告してよい」という証明（最大の長さも書く）
ROV
受け取った経路を ROA と照合すること
Valid／Invalid／NotFound
一致／矛盾（捨てる）／ROA が無い（通常は受け入れる）
経路ハイジャック
他人のアドレスを広告して通信を奪う
ルートリーク
広告してはいけない相手に経路を流してしまう
ASPA
上流の AS を登録し、経路の途中の偽装・漏えいを見つける

ネスペならこう問われる

  1. ROA に登録する情報は？
    解答例

    プレフィックス、許可する最大プレフィックス長、広告してよい起点の AS 番号。

  2. 正規の AS から広告されたのに Invalid になる例は？
    解答例

    ROA の最大プレフィックス長より長いプレフィックス（例：/24 まで登録しているのに /25 で広告した）。

  3. 攻撃者が正規の AS 番号を起点に見せかけて広告すると、ROV では防げない理由は？
    解答例

    ROV は起点の AS 番号しか検証せず、AS_PATH の途中の経路が正しいかは検証しないから。

AI データセンターのネットワーク

GPU 同士を RDMA（RoCEv2）で結ぶ。パケットが1個落ちると全体が待たされるので、ロスレスにする。

なぜ今　生成 AI の学習用に、国内でも大規模な GPU データセンターの建設が相次いでいる。400G／800G イーサネットや、AI 向けの新規格 Ultra Ethernet（2025年に仕様 1.0）が登場した。

知っておくべきキーワード

RDMA
CPU を通さず、相手のメモリへ直接読み書きする
RoCEv2
RDMA を UDP/4791 で運ぶ → ルータを越えられる
PFC（802.1Qbb）
優先度ごとに一時停止フレームを送り、バッファあふれによる損失を防ぐ
ECN・CNP・DCQCN
スイッチが混雑の印 → 受信側が通知 → 送信側が速度を落とす
スパインリーフ・ECMP
どのサーバ間も同じホップ数。等コストの経路に分散する
エレファントフロー
大容量で長く続くフロー。ECMP の偏りの原因になる
Ultra Ethernet
AI 向けの新しいイーサネット仕様（2025年に 1.0）

ネスペならこう問われる

  1. RoCEv2 が、ルータを越えて通信できる理由は？
    解答例

    RDMA のデータを UDP/IP でカプセル化しているから（宛先ポート 4791）。

  2. PFC はどうやってパケットの損失を防ぐ？
    解答例

    スイッチのバッファがあふれそうになると、優先度クラスごとに送信元へ一時停止（PAUSE）フレームを送り、送信を止めさせる。

  3. PFC だけに頼らず ECN も使う理由は？
    解答例

    PFC の一時停止が上流へ連鎖すると、無関係な通信まで止まる（デッドロックや HoL ブロッキング）ため、ECN で早めに送信側の速度を落とす。
